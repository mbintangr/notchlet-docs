Flags worth memorizing

FlagWhy
--revision <n>Reject stale writes with revision_conflict before anything changes.
--recordTurn an executed verification into evidence. Required to claim coverage.
--serveLet verification own start, readiness, and shutdown of the app.
--treeVerify every open node deepest-first, then by path, or render/sync a whole subtree. Verify exits 1 when any node fails and 2 when no open node has a runnable check.
--repeat <n>Detect state-dependent failures by rerunning the batch.
--require-evidenceHard-block task completion without current passed evidence.
--previewRead-only closure report with recovery commands.
--fail-on-blockersWith close --preview, exit 1 while blockers remain so CI can gate closure.
--jsonMachine envelope for scripting; for verify, read data.result.
--workspace <root>Select a workspace explicitly instead of the nearest one.
--dry-runValidate a plan import without writing.
--baseline-revision <n>Required to close standard and delta changes.

Check kinds and assertions

KindUseAssertions
commandTests, linters, type checks, scripts.Non-zero exit fails; --working-directory sets the directory.
httpEndpoints and health probes.Status, body contains, JSON subset/containment/path, headers.
uiRendered behavior.Visibility, enabled state, title, scoped text, interaction steps; captures on failure.
browserLegacy alias.Runs as an HTTP probe.
manualHuman attestation.Skipped during verify; requires recorded evidence.

--expected-json compares a length-strict recursive subset. --expected-json-contains allows extra object keys and unordered extra array items, but an empty expected array proves the observed array is empty; it does not match a non-empty array. Use --expected-json-at for explicit path predicates such as counts and scalar ranges.

Tree verification runs runnable nodes deepest-first, then by path, and reports the run order plus each node's observation basis. It does not isolate workspace, environment, or external application state; use per-node setup/teardown or separate data directories for stateful checks. It skips archived nodes, bare rollups, and nodes with only manual checks, exits 1 when a node fails, and exits 2 when no open node has a runnable check.

Change schemas

Quick

  • Use for small, local, no-capability work.
  • Declare --capability-impact none with a rationale.
  • Close without a baseline revision.

Standard

  • Use for features or capability changes.
  • Substantive design, at least one decision with rationale, every requirement covered by a scenario.
  • Capture a baseline; declare a delta or no-impact rationale.
  • Close with --baseline-revision.

States at a glance

Change lifecycle

Draft planning → validated (ready) → executing tasks → verified → closed/archived. Revisions advance on authoring writes; rendering writes once; execution metadata changes are reported as execution drift.

Evidence freshness

StateTreatment
current passedSatisfies completion and closure.
failedBlocks until fixed and re-run.
staleBlocks; rerun deliberately.
unknownBlocks until re-verified (for example a truncated Git observation).
missingBlocks when policy requires evidence.

Freshness basis is git or artifact. Artifact-bound evidence can close without a Git repository.

Error and recovery reference

SignalMeaningRecovery
revision_conflictThe write used a stale revision.Reread, reconcile, retry with the current revision.
stale / unknown verificationEvidence no longer reflects current state.Run the printed recovery command or verify --record.
missing evidenceNo observation references the work.Verify with --record and explicit links.
baseline missingStandard/delta change not baselined.notchlet change baseline <change>.
undeclared capability deltaStandard change without a declaration.Declare no-impact with rationale, or author delta operations.
plan driftThe imported plan changed since acceptance.Review plan status, then plan sync or accept at close.
server reused unexpectedly--serve found a listener it does not own.Stop it or pass --reuse-serve knowing setup is skipped.
non-idempotent setupSetup changed state on the second run.Fix setup, declare --setup-state, re-run the idempotence check.
JSON envelope

--json reports command execution in ok. For verification, the result lives in data.result or data.verification.outcome; a successful command can still be a failed verification.

Pre-flight checklists

Before planning

  • Product and item resolved and confirmed, or no duplicates locally.
  • Source documents or tickets read.
  • Outcome understood; blocking ambiguity asked, not assumed.
  • Existing changes checked with change list.

Before implementing

  • Status is TODO or IN_PROGRESS.
  • Dependencies resolved or marked non-blocking.
  • Acceptance criteria measurable and testable.
  • Package scripts and existing patterns located.

Before completing a task

  • The verification evidence exists and is current.
  • Focused checks pass; pre-existing failures documented.
  • Changed files reviewed for secrets and artifacts.
  • No unrelated items modified.

Before delivery

  • Review approved or not required.
  • PR or MR verified merged for branch-linked work.
  • Parent stays open while children are open.
  • Explicit authorization for push, merge, status, or deploy.
