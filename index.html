Notchlet documentation

Requirements in, verified changes out.

Notchlet is a requirements and workflow system for software work. A connected platform holds products, backlog items, documents, and delivery state. A local CLI turns any of those into a revisable change with requirements, checks, tasks, and recorded evidence — so a task is only complete when something actually ran.

What Notchlet is

Notchlet has four cooperating parts. You can use the local parts with no account, and add the platform when you want shared product context and delivery state.

Platform

The source of product requirements and work status: products, epics, stories, tasks, documents, tickets, Git issues, comments, and development delivery evaluation.

The core idea: a change is the unit of work

A change is a small, self-describing contract between intent and evidence. It records what you mean to build, how you will know it works, and what actually ran:

change
├── intent and outcome
├── requirements      what must be true
├── acceptance scenarios   when / then
├── design decisions  why this approach
├── checks            runnable commands, HTTP probes, UI assertions
├── tasks             ordered work with dependencies
├── run metadata      run command, preview, readiness, environment
└── evidence          current, scoped, and fresh observations

Every authoring write is revision-guarded. Completion is gated on current passed evidence, not on optimism. Local verification, local closure, remote delivery, merge, and deployment are separate outcomes and are never conflated.

Evidence over assertions

A check that never ran is not a passing check. notchlet verify executes declared checks; --record turns the result into evidence linked only to what was executed. Stale, failed, unknown, or missing evidence is a blocker until re-verified.

Three ways to work

Offline, local-first

No account, no MCP, no network. Initialize a workspace and drive a change entirely with the CLI. Ideal for solo work, spikes, and CI-local verification.

notchlet init
notchlet change new docs-refresh --quick
# author, task, verify, close

Connected to the platform

Log in, configure MCP for your client, resolve a backlog item by key or title, import it as a change, and let agents read bounded context while the CLI owns local state.

notchlet auth login --server <url>
notchlet mcp configure --client opencode
notchlet backlog import NOT-123

Platform-first

Plan epics, stories, and tasks in the web app, attach documents and tickets, then hand work to an agent that resolves the item and records evidence back.

MCP handles remote context and authorized writes; the CLI handles local change and evidence state.

Agent-driven

Install the skills, then ask for the outcome. notchlet-super reads current state and routes to plan, implement, review, or deliver without replaying setup.

notchlet client init opencode --apply

The loop

backlog item ──import──▶ change ──plan──▶ requirements + checks + tasks
                              │
                     implement│
                              ▼
                         run checks ──▶ evidence (current, scoped)
                              │
                     review ──┴──▶ close (local) ──sync/deliver──▶ PR / status

  1. Resolve the work

    Use a local change, or search the platform by key or title and import it. Read the item and its bounded context — not the whole backlog.

  2. Plan to Definition of Ready

    Write intent, outcome, measurable requirements and scenarios, design decisions, runnable checks, and ordered tasks. notchlet validate reports every gap.

  3. Implement and verify

    Start tasks with revision checks, implement the behavior, then let verify --serve own the app lifecycle and record evidence.

  4. Review and close

    Review against acceptance criteria, close locally with change close, and handle remote delivery only when explicitly authorized.

Quickstart (offline)

Requires Node.js 22 or newer. The CLI reports its own version and the core engine version it embeds.

npm install -g @notchlet/cli
notchlet --version
# notchlet 1.1.2 · @notchlet/core 1.1.0

mkdir my-project && cd my-project
notchlet init

notchlet change new first-change --quick
notchlet change update first-change \
  --capability-impact none \
  --capability-rationale "Local-only first change; no product capability changes."
notchlet change update first-change \
  --intent "Prove the workflow end to end." \
  --outcome "A served page that passes a check with recorded evidence."
Do not hand-edit authored state

Use notchlet change add, change update, and change apply instead of editing tasks.json. Direct edits bypass validation and are reported as authored artifact drift.

Ground rules

  • Completion needs evidence. A task is complete after its verification evidence exists, not after code is written.
  • Revisions protect intent. Pass --revision on authoring writes so stale edits fail before anything changes.
  • Authorization is explicit. Ticket ownership is not permission to push, open or merge a PR, deploy, or publish. Ask first.
  • Secrets stay out of config. Remote MCP entries reference the token through an environment variable; never inline it.
  • Read before you write. Fetch bounded context for the item you need; do not dump a whole product to find one entry.
