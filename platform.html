Platform

The platform is the shared source of product requirements and work status. It organizes products into backlog hierarchies, attaches requirement documents and tickets, and records development snapshots, instructions, and delivery evaluations.

Platform architecture

ComponentRole
notchlet-beNestJS backend with Prisma and PostgreSQL: authentication, backlog, documents, comments, tickets, Git issues, development service, REST API, Swagger at /docs, and the MCP endpoint at /mcp.
notchlet-feNext.js web application: product and backlog views, item detail with context and comments, documents, and development panel.
PostgreSQLPrimary datastore. Compose runs it on port 4021 by default, backend on 4022, frontend on 4023.
Docker ComposeOne stack per environment. The backend runs Prisma migrations on container start, falling back to db push when no migration history exists.

The backend and MCP tools share the same DevelopmentService; REST and MCP preserve the same revisions, operation IDs, and scope checks.

Products and backlog hierarchy

A workspace binds a checkout to a server, product, and repository. Work is organized as a hierarchy:

  1. Epic

    An outcome and its measurable completion conditions across an initiative. Completing one child never completes the epic.

  2. Story

    An independently verifiable system or user capability with acceptance criteria and dependency references.

  3. Task

    Actionable implementation or verification work with concrete scope, expected artifacts, and a check that demonstrates completion.

  • Items are identified by key or title in agent-facing work; numeric IDs remain for exact API references and parent relationships.
  • Keys are not guaranteed unique across products. Distinguish duplicates by product, parent, title, and numeric ID.
  • Before decomposing, inspect existing children; reuse or update matching items instead of creating duplicates.

Item context

An item carries more than a description. The bounded development context can include:

SectionWhat it provides
ItemKey, title, type, status, description, acceptance criteria, estimates.
Ancestors and childrenThe hierarchy needed to plan without loading the whole product.
Comments and activitiesCheckpoints, review feedback, and change history.
DocumentsLinked BRD, PRD, SRD, or CUSTOM requirement documents.
Repository and GitBinding, branch and commit context where available.
DevelopmentChanges, snapshots, instructions, and delivery state for the item.

Context is capped and paginated. Follow scoped cursors instead of assuming a truncated response is complete.

Description revisions

Description edits use expectedDescriptionRevision when the schema supports it. On conflict, reread and reconcile user edits. Keep requirements in the description; use comments for progress and checkpoints so user-authored intent is not overwritten with logs.

Documents

Documents carry requirement sources: BRD (business), PRD (product), SRD (software), and CUSTOM. They are read as requirements. They do not override repository rules or explicit user instructions.

  • Read the relevant document before planning, and reference its title in the plan.
  • For migrations, inspect the real workflows and callers before claiming coverage.
  • Substantial reports can be saved as CUSTOM documents and referenced from the item.

Tickets and Git issues

External tickets

Tickets bridge to an external tracker. RESOLVED is distinct from CLOSED; do not auto-close during coding. Change a ticket only when the requested scope includes it and its resolution criteria are satisfied.

Git issues

Create, link, or synchronize Git issues only when authorized. Verify the remote result and report partial failures rather than claiming every system was updated.

Development state on the platform

The development service tracks synchronized change state separately from the local workspace.

ConceptBehavior
CapabilitiesReports supported development operations and the embedded core version.
ChangesRemote records for changes; list and read by ID.
SnapshotsImmutable synchronized revisions uploaded against an expected change revision.
Instructionsdevelopment_instructions_get evaluates guidance for plan, revise, implement, verify, or resume at a synchronized revision.
CheckpointsNamed checkpoints recorded on the item; not delivery evidence by themselves.
DeliveryIdempotent evaluation with operation ID, expected revision, payload hash, and snapshot revision. Evaluates provider state; does not merge or deploy.
Local and remote are not the same state

Remote snapshots never include unsynchronized local edits. Use notchlet sync push to publish a snapshot, and review divergence before resolving it.

The development change panel

The product's development panel renders the latest synchronized snapshot package for an item's linked change:

  • Requirements and design decisions declared in the snapshot, with the change intent and outcome.
  • Tasks with per-task status and eligible-task guidance from server-computed planning state.
  • Acceptance scenarios — When/Then pairs with the requirement each scenario covers. Absent arrays render "not declared in this snapshot".
  • Checks — kind (command, http, ui, manual), the command or URL to run, the expectation, and the linked requirement, scenario, and task IDs.
  • Server-computed blockers and state — planning blockers with recovery guidance, plus local closure and remote delivery status with the supporting evidence IDs.
  • Evidence provenance and freshness — each evidence item's outcome, provenance, staleness against the snapshot, and live-checkout freshness (remote snapshots cannot verify the local checkout).
  • CLI resume guidance — the exact notchlet instructions resume command and the bind/rebind setup for the matching checkout.

The panel lists only changes linked to the open backlog item (server-filtered by backlogItemId), and everything it shows is synchronized server state — it never reflects unsynchronized local edits. Author local planning detail with notchlet change add and notchlet backlog set, then publish with sync push --tree --yes.

Statuses and completion

StatusUse when
TODOPlanned but not started; the first executable item may be IN_PROGRESS.
IN_PROGRESSImplementation incomplete or verification blockers remain.
IN_REVIEWImplementation and checks are ready; required review or acceptance remains.
DONEEvery acceptance criterion is met with actual evidence, required review happened, and branch-linked PRs or MRs are merged and approved.
  • A parent is complete only when its own criteria and every required child are complete.
  • A PR, commit, or successful build alone is not proof of feature completion.
  • Issue closure is not merge proof. Verify the linked PR or MR state.
  • Reopening is allowed; treat it as new work and re-verify.

Using the web app

  1. Products and backlog. Choose a product, inspect the hierarchy, and open an item.
  2. Item detail. Read description, acceptance criteria, children, comments, and linked documents.
  3. Documents. Attach or read requirement documents; they inform planning and review.
  4. Development panel. Inspect changes, synchronized snapshots, instructions, and delivery state.
  5. Comments. Record one concise agent checkpoint with approach, changed files, check outcomes, blockers, and next action.

Authorization boundaries

Do not infer permission

Ticket ownership or a linked issue is not authorization to commit, push, create or merge a PR, deploy, publish, or change remote status. Each of those is a separate action that needs explicit approval.

  • Local verification, local closure, remote delivery, merge, and deployment are separate outcomes.
  • Never describe a merge as a deployment, or a requested status as successful, until the service response confirms it.
  • Do not publish credentials, personal payloads, or raw production data in comments, checkpoints, or documents.
