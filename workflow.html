Practice

Development workflow

The Notchlet workflow is a loop, not a checklist you replay. Read current state, take the smallest correct action, prove it with executed checks, and only then change status or deliver.

The lifecycle

  read state ──▶ resolve work ──▶ plan ──▶ implement ──▶ verify ──▶ review ──▶ close
       ▲                            │                                                │
       │                            └──────── revise / resume ──────────────────────┘
       │                                                                             │
       └────────────────────────── sync / deliver (authorized) ◀─────────────────────┘

Every phase is revisitable. Revision checks protect against stale edits, and evidence is revalidated whenever the change moves forward.

Phase 0 — Read current state

Do this before anything else. Most wasted work comes from restarting setup or replanning work that already exists.

notchlet status <change>
notchlet instructions <change> --action resume
notchlet change list
notchlet workspace info
  • Reuse the identified workspace, product, repository, backlog item, and active change while they remain valid.
  • Only initialize a workspace when none exists and the user approves it. There is no separate bootstrap command.
  • Only configure MCP when credentials or connection settings are genuinely missing.
The router decides

notchlet-super turns intent plus state into the smallest action: explore, plan, resume, revise, implement, review, or deliver. Exploration and planning do not require initialization, a hierarchy, or application writes.

Phase 1 — Resolve the work

Connected backlog work

  1. Resolve the product and repository binding with workspace info.
  2. Search by key or title; read the matching item and its bounded context.
  3. Confirm product, parent, and title before creating anything.
  4. Import only when no matching local change exists:
notchlet backlog import NOT-123
notchlet backlog import NOT-123 --tree --dry-run
notchlet backlog import NOT-123 --tree
notchlet status NOT-123
notchlet instructions NOT-123 --action plan

--tree follows platform children with cursors and scaffolds ancestor shells for mid-level items. Each imported node keeps its own change, and a re-import reuses nodes by backlog item ID. Locally authored trees push in the same order: parents first, then children, adopting a matching platform item instead of duplicating it. Final status changes are explicit and bottom-up:

notchlet sync push --change user-auth --tree --yes
notchlet sync pull --change user-auth --tree
notchlet sync deliver --change user-auth --status DONE --with-children

Local task completion and checkpoints never set a backlog item to DONE; delivery is the only status target that does. Flat changes written before the hierarchy existed remain readable. Preview notchlet migrate to see how unlinked changes would move under legacy/ and how linked flat changes would re-home under the tree, then apply when the plan is acceptable.

Local-only work

notchlet change new user-auth --as epic
notchlet change new login --as story --parent user-auth
notchlet change new login-form --as task --parent user-auth/login
notchlet change tree
notchlet status user-auth/login --tree

Every backlog node is a full change, so the same checks, evidence, verify, and close flow applies at the leaf. Author leaf work — tasks and their requirements, scenarios, checks, intent, and outcome — on the leaves in one pass: create requirements and tasks first, then add each check with --requirement, --scenario, and --task together. Verify warns when checks have no task link, because unlinked evidence may not satisfy task completion. A parent is a rollup whose acceptance is its closed children, so it needs no leaf planning content of its own; it may declare optional acceptance checks, which must be current before it closes. Flat legacy changes remain readable and can live alongside trees.

Import a whole validated tree with notchlet change new --from tree.json --dry-run. The plan nests itemType nodes with an optional plan per node; all nodes are type-checked and path-checked before any directory is written, and a failed import rolls back the nodes it created. Reruns are idempotent: a node already at the same path with the same type and title is reused, so re-importing does not duplicate work. Imported nodes keep the tree file as their plan provenance, so change plan status validates the whole tree and flags a node that was removed or renamed in it.

Check for an existing change first with change list. Reuse and refine instead of duplicating.

Phase 2 — Plan to Definition of Ready

Planning stays lightweight, but it must be measurable. A story or task is ready only when all of these hold:

  • Acceptance criteria are written and measurable (given/when/then or equivalent).
  • Dependencies are listed, or marked none.
  • Scope is specific: capability, route, or component is named.
  • Verification criteria say what test or evidence proves completion.
  • No unresolved blocking dependency remains.
notchlet change update my-change \
  --intent "Expose search over items." \
  --outcome "GET /search?q= returns matching names in order." \
  --capability-impact none \
  --capability-rationale "Docs-only or internal work; no shipped capability changes."

notchlet change add my-change requirement --id R1 \
  --title "Search endpoint" --description "Returns items whose name contains q."
notchlet change add my-change scenario --id S1 \
  --when "q matches two items" --then "both are returned in name order" --requirement R1
notchlet change add my-change decision --id D1 \
  --decision "Use a single SQL query." \
  --rationale "Avoids N+1 reads and keeps ordering deterministic."
notchlet change add my-change check --id C1 \
  --description "Search tests" --kind command \
  --command "node --test test/search.test.mjs" --requirement R1 --scenario S1
notchlet change add my-change task --id T1 \
  --title "Implement endpoint" --requirement R1

notchlet validate my-change
notchlet change render my-change --write

Render model-derived artifacts before verifying so verification and closure observe current canonical files. Plain --write updates drifted generated artifacts, but refuses hand-authored files without the generated-content marker; review those and add --force only when replacing them is intended.

Rollups delegate acceptance

Intent, outcome, and requirements are leaf obligations. A parent with children is validated as a rollup: unfinished leaf planning on the parent is not a blocker, and its closure acceptance is the set of closed child closures. Rollups may declare optional acceptance checks; any declared rollup check must still be current before it closes. Closed rollup manifests record the accepted child closures, including their paths, hashes, and verification status. EPIC and STORY scaffolding seeds intent and outcome so the narrative is never silently blank; a rollup with both blank still closes, but the preview prints an advisory. Closure stores the authored intent and outcome as narrative in closure.json and prints Intent/Outcome in closure.md. Each closed parent also records descendant totals — nodes, leaves, requirements, checks, current evidence, and completed tasks — in closure.json and closure.md without changing the direct child records.

SchemaAdditional planning requirements
QuickCapability impact none with a rationale for no-impact work, or an explicit delta.
StandardSubstantive design content, at least one decision with rationale, every requirement covered by a scenario, baseline capture, and a declared delta or no-impact rationale.

Declare run metadata at planning time so verification is reproducible:

notchlet change update my-change \
  --run-command "node server.mjs" \
  --preview-url "http://127.0.0.1:4173/" \
  --readiness-url "http://127.0.0.1:4173/health" \
  --ready-timeout 20000 --ready-interval 100 \
  --environment PORT=4173

Phase 3 — Implement

  1. Confirm the repository, branch, and clean or intentional working state (git status --short).
  2. Set the item or change to IN_PROGRESS when implementation starts.
  3. Start the task with a revision check so stale work is caught early.
  4. Implement complete behavior: validation, failure paths, authorization, and caller integration.
  5. Run focused checks and distinguish pre-existing failures from new ones.
notchlet task start T1 --change my-change
# implement
node --test test/search.test.mjs
notchlet task complete T1 --change my-change --require-evidence
Do not mark complete on intent

Completion warns without current passed evidence; --require-evidence turns that warning into a hard block. Reopening stays ungated, but the task must be re-verified.

Phase 4 — Verify with evidence

Let verification own the app lifecycle so checks start from a known state:

notchlet verify my-change --serve --record
notchlet verify my-change --serve --repeat 2         # detect state-dependent failures
notchlet verify my-change --record --capture-url http://127.0.0.1:4173/ --full-page
notchlet verify user-auth --tree --serve --record   # every open node, bottom-up
notchlet evidence list --change my-change --task T1
ObservationMeaning
passed, currentExecuted against the current state; can satisfy completion and closure.
failedThe check ran and failed. Fix the cause or record the blocker.
staleThe observed state changed; re-run deliberately.
unknownFreshness could not be established, for example a truncated Git observation. Blocks closure until re-verified.
missingNo evidence references the work. Run the check with --record.
  • Git repositories bind evidence to a repository identity and tracked/untracked source digest; .notchlet, dependencies, build output, environment files, and credentials are excluded. A non-Git workspace binds each evidence item to a bounded workspace source fingerprint (hashes only), so ordinary source edits still stale it. Legacy evidence without a Git observation or fingerprint stays fresh but source-unbound.
  • Closure preview prints Source binding. If current evidence is source-unbound, closure blocks with artifact_basis_unacknowledged: re-record checks after binding source, or pass change close --accept-artifact-basis to record the artifact-only decision explicitly in the closure manifest.
  • Use --setup, --save-setup, and --check-setup-idempotence when state must be reset or reproduced. Setup runs before checks; when it also starts the app, verify recognizes that listener instead of starting a second one.
  • Prefer an owned --serve run; --reuse-serve can hide drift and skips setup.
  • Use --tree to verify every open node with its own checks and persisted run metadata. Nodes run deepest-first, then by path; the output names that run order and the observation basis. Runtime flags such as --record, --serve, --timeout, --environment, --repeat, --ui-capture, and --full-page apply to every node. Archived nodes, bare rollups with no runnable checks, and nodes with only manual checks are skipped; manual checks still need separately recorded evidence. Failed nodes name the failed check IDs, failed assertions, failure phase, evidence log path, and single-node recovery. The command exits 1 when any node fails and 2 when no open node has a runnable check; an archived-only subtree exits 2 with no_open_nodes and a change restore recovery. Per-check selection and assertion overrides, setup and serve overrides, and --capture-url/--attach are rejected with --tree; verify a single node for those.
  • Tree runs are not hermetic: nodes share the workspace, environment, and any external app or data they touch, and the deepest-first order is not the same as task dependency order. Reset state with each node's own setup/teardown or isolated data directories when checks are stateful.
  • UI checks distinguish perception from presence. --expected-hidden-selector passes for hidden or absent elements, --expected-absent-selector requires true DOM absence, and --expected-visible-selector proves the intended view rendered. A sole check that only asserts hidden or absent state raises a hidden_only_sole_check advisory; add a positive assertion or a second check.
  • If all nodes share one running app, start it once with verify <node> --serve --keep-running and verify the other nodes individually with --reuse-serve; stop the app yourself when finished.
  • Recovery commands printed by the CLI must be run deliberately; they are never applied automatically.

Phase 5 — Review

Review happens after implementation and before delivery. Self-recorded checks are not independent review.

Requirements coverage

  • Every acceptance criterion is addressed.
  • No scope creep beyond what was requested.
  • Edge cases and failure behavior are handled.

Code quality

  • No secrets, credentials, or personal data in the diff.
  • No build artifacts, dependency folders, or local config committed.
  • Existing abstractions reused; no unnecessary new ones.

Testing

  • Lint, type-check, and focused tests pass.
  • Test output is actual, not assumed.
  • Pre-existing failures are identified separately.

Backlog consistency

  • Item description matches implemented behavior.
  • Description edits used the expected revision.
  • One concise checkpoint comment records approach and outcomes.

Approve only when all checks pass; set the item to IN_REVIEW or keep it there and let delivery proceed. Request changes with specific feedback and return to implementation. Re-review only changed files and the feedback items.

Phase 6 — Close and deliver

Closure preview is read-only and reports every dimension separately:

notchlet change close my-change --preview
notchlet change close my-change --preview --fail-on-blockers   # CI gate; exits 1 on blockers
notchlet change close my-change                          # quick no-impact changes
notchlet change close my-change --yes                    # skip the confirmation prompt
notchlet change close my-change --baseline-revision 3    # standard and delta changes
  • Standard and delta changes require the captured baseline revision. Quick no-impact changes close without one.
  • --preview exits 0 by default so the report is inspectable; add --fail-on-blockers when CI should fail while blockers remain.
  • Every blocker includes a recovery command or recovery tool; run it deliberately.
  • Local closure is not remote delivery. Delivery evaluates existing provider state and does not merge or deploy.
  • For branch-linked work, a DONE request requires the exact linked PR or MR to be merged and approved.

Delivery sequence

  1. Persist evidence

    Record a meaningful checkpoint with approach, changed files, exact commands and outcomes, blockers, and next action. Never include credentials.

  2. Sync deliberately

    notchlet sync push --change my-change. On divergence, review local artifacts before sync resolve --keep-local.

  3. Evaluate delivery

    Use development_delivery_create with expected revision, operation ID, payload hash, and snapshot revision. Query the operation after an uncertain response.

  4. Confirm the returned state

    Report the status the service returned. Do not describe merge as deployment or a requested status as successful before confirmation.

Revision discipline

  • Pass the revision you read: --revision <n> on authoring writes, removes, converts, applies, and task transitions.
  • A stale write returns revision_conflict before anything changes. Reread, reconcile, and retry.
  • Editing a requirement invalidates its delta snapshot; re-author the delta operation.
  • Rendering artifacts bumps the revision once; re-check drift afterwards with change render --check.

Anti-patterns

  • Replaying initialization or replanning when valid state already exists.
  • Hand-editing tasks.json or other authored state instead of using the CLI.
  • Dumping a whole product to find one backlog item.
  • Inventing MCP tool names, comments, or results that the live schema does not support.
  • Treating a successful build, a commit, or an opened PR as feature completion.
  • Pushing, merging, deploying, or changing status because a task finished.
  • Putting tokens, credentials, or production payloads in config, prompts, comments, or evidence.
  • Auto-running recovery commands without reviewing what they change.

Definition of done

Before delivery
  • Every acceptance criterion is met with actual evidence.
  • Focused checks pass, with pre-existing failures documented separately.
  • Review is approved, or review is not required by policy.
  • Branch-linked work has a verified merged PR or MR; issue-only work is committed.
  • No unresolved blockers remain; evidence is current, not stale or unknown.
  • Parents stay open while required children are open.
