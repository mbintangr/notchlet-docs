Foundations

Core concepts

The local model is small and strict: a workspace contains changes, a change contains authored intent and runnable checks, and completion is defined by current evidence. Understanding these objects makes every command predictable.

Workspaces

A workspace is any directory containing a .notchlet directory. The CLI uses the nearest initialized workspace, or an explicit --workspace <path> (also --root). Initialization is deliberately boring:

notchlet init              # local-only, no account
notchlet init --interactive   # choose server, org, product, repository
notchlet init --local --client opencode   # local mode plus skills and local MCP config

Initialization writes only the workspace and its change directory, plus local guidance files. It does not require a bootstrap step, and using an existing workspace is always preferable to initializing a new one.

What lives on disk

PathPurpose
.notchlet/changes/<change>/The change model and its artifacts: canonical proposal.json, spec.json, state tasks.json, and authored design.md.
.notchlet/.local/Machine-local state: sync journals, close journal and lock, mcp.json, and client guidance snapshots. Never shared; excluded from evidence fingerprints.
AGENTS.md, PROMPT.md, .notchlet/README.mdGuidance written during initialization so agents know how to use the workspace.
.notchlet/changes/<change>/design.mdAuthored design narrative; the canonical model stays authoritative.
Edit through the CLI

Use change add, change update, change remove, change apply, and the task commands. Hand-editing tasks.json bypasses the model; execution metadata edits are reported as execution drift without advancing the revision.

Changes and revisions

A change is the unit of planned work. It carries identity, intent, outcome, the requirement and check model, tasks, run metadata, capability declaration, evidence policy, and a revision counter.

FieldMeaning
id / nameStable identifier and friendly name. Commands accept either.
modequick or standard. Standard changes require substantive design content, design decisions, a capability baseline, and full requirement coverage.
intent / outcomeWhy the change exists and the observable result. Outcome should be measurable.
revisionMonotonic authoring revision. Pass --revision on writes to reject stale edits with revision_conflict.
contentRevisionRevision of authored content specifically.
executionSha256Fingerprint of execution metadata; changes are reported as execution drift.
evidencePolicyperTask warns at each task completion before evidence exists; endOfChange suppresses those warnings when one final batch covers everything.

Two changes can share a name across different workspaces; keep the workspace root in mind when scripting.

Authored items

Five kinds of content are authored through the CLI. Each has a stable ID and cross-references other items.

KindPurposeKey options
requirementWhat must be true, as measurable behavior.--id, --title, --description
scenarioGiven/when/then acceptance statement linked to a requirement.--id, --when, --then, --requirement
decisionDesign choice and rationale. Standard changes require at least one.--id, --decision, --rationale
checkExecutable evidence: command, HTTP probe, UI assertion, or manual attestation.--kind, --command, --url, expectations, links
taskOrdered implementation work with dependencies.--id, --title, --requirement, --depends-on
 
notchlet change add my-change requirement --id R1 \
  --title "Search returns matching items" \
  --description "GET /search?q= returns only items whose name contains q."

notchlet change add my-change scenario --id S1 \
  --when "a query matches two items" --then "both are returned in name order" \
  --requirement R1

notchlet change add my-change check --id C1 \
  --description "Search integration test" --kind command \
  --command "node --test test/search.test.mjs" --requirement R1 --scenario S1

notchlet change add my-change task --id T1 \
  --title "Implement search endpoint" --requirement R1

Check kinds and assertions

KindBehaviorAssertions
commandRuns a shell command in the workspace or a declared working directory.Exit code; non-zero fails. Output is recorded.
httpProbes a URL.--expected-status, --expected-body-contains, JSON subset/containment/path, headers.
uiBrowser-level assertions against a served page.Visibility, enabled state, title, scoped text, declarative interactions; captures archived on failure by default.
browserLegacy alias that runs as an HTTP probe.HTTP assertions.
manualReported as skipped during execution.Requires separately recorded evidence.

Checks can declare --requirement, --scenario, and --task links. Verification records only executed checks and their declared or explicitly selected links; unrelated work is never claimed.

Tasks, dependencies, and evidence policy

Tasks move through an ordered lifecycle. Starting and completing are revision-checked so two agents cannot silently overwrite each other.

notchlet task start T1 --change my-change
notchlet task complete T1 --change my-change --revision 12
notchlet task complete T1 --change my-change --require-evidence   # hard block without current passed evidence
notchlet task complete --all --change my-change                   # remaining tasks in dependency order
notchlet task update my-change T2 TODO --force                    # deliberate out-of-order transition
  • Completion warns when no current passed evidence references the task. Use --require-evidence when policy requires a hard block.
  • Reopening stays ungated; a reopened task must be re-verified before closing again.
  • --depends-on orders tasks; --all completes remaining tasks under one revision.

Run metadata and the serve lifecycle

A change can declare how its app runs, is previewed, and becomes ready. Verification then owns that lifecycle instead of assuming a server is already up.

notchlet change update my-change \
  --run-command "node server.mjs" \
  --preview-url "http://127.0.0.1:4173/" \
  --readiness-url "http://127.0.0.1:4173/health" \
  --ready-timeout 20000 --ready-interval 100 \
  --environment PORT=4173
OptionEffect
--run-commandStarted by verify --serve; stopped afterwards unless --keep-running.
--readiness-urlPolled until success or timeout before HTTP/UI checks run.
--environment KEY=valueReproducible variables passed to served, setup, teardown, and check commands.
--setup / --teardownCommands around the check batch. Persist setup with --save-setup.
--repeatReruns the batch (including setup) and reports state-dependent failures.
--check-setup-idempotenceRuns setup twice and fails when declared state paths change.
--reuse-serveAllows targeting an already-running server the run does not own; setup is skipped.

Verification and evidence freshness

Verification has three layers: the declared check, the observation of its result, and the evidence record that links observations to requirements, scenarios, and tasks.

notchlet verify my-change --serve --record
notchlet verify my-change --check C1 --repeat 2
notchlet verify my-change --record --capture-url http://127.0.0.1:4173/
notchlet evidence list --change my-change --task T1
notchlet evidence list --change my-change --stale
  • Freshness basis. Evidence is bound to git or artifact observations. Artifact-bound evidence can satisfy closure without a Git repository.
  • Freshness states. Evidence can be current, stale, failed, or unknown. Stale, failed, unknown, and missing evidence block closure until re-verified.
  • Recovery is deliberate. Recovery commands printed by verify, evidence list, status, or closure preview are never executed automatically.
  • Scoped claims. --requirement, --scenario, and --task require --record and only link what the run actually covered.
Outcomes are separate

Local verification, local closure, remote delivery, merge, and deployment are distinct. Closing a change does not mean a PR is merged, and a merged PR does not mean anything was deployed.

Capability closure

Capability classification keeps trivial work cheap and makes real capability changes explicit.

ClassificationWhenClosure requirements
noneQuick change that declares --capability-impact none with a non-empty rationale.No baseline, no delta operations.
deltaThe change declares explicit capability delta operations.Baseline revision plus delta operations; close with --baseline-revision.
standardAny other standard change.Baseline capture; close with --baseline-revision.
 
notchlet change baseline my-change
notchlet change delta my-change add --requirement R1 \
  --rationale "Search capability now returns ranked matches."
notchlet change delta my-change update --requirement R1 \
  --rationale "Ranking ties are broken by name."
notchlet change delta my-change delete --requirement R1

Delta operations snapshot the authored requirement and its linked scenarios. If you edit them afterwards, re-author the operation so the snapshot matches. notchlet change close my-change --preview is read-only and reports planning, verification, local closure, and remote delivery separately, with a recovery command for every blocker.

Synchronization

Sync moves a change snapshot between the local workspace and the connected server. It is explicit, revision-aware, and separate from closure.

notchlet sync mode auto|manual
notchlet sync status --change my-change
notchlet sync push --change my-change
notchlet sync pull --change my-change
notchlet sync resolve --change my-change --keep-local
  • Divergence requires review before resolving; --keep-local discards the remote side and must be a deliberate decision.
  • Remote snapshots do not represent unsynchronized local edits.
  • notchlet checkpoint --change my-change --name "..." records a synchronized checkpoint; it is not delivery evidence by itself.

Statuses

StatusMeaning
TODOPlanned, not started.
IN_PROGRESSImplementation started, or verification blockers remain.
IN_REVIEWImplementation and checks are ready; review or acceptance remains.
DONECompletion conditions met, including required review and evidence. Parents stay open while required children are open.

Security and secrecy

  • MCP credentials are references, not literals: use {env:NOTCHLET_MCP_TOKEN} (OpenCode) or ${NOTCHLET_MCP_TOKEN} (Claude Code) in config.
  • notchlet mcp token prints the generated credential only on explicit invocation; treat it as a secret.
  • Never place tokens or credentials in CLI arguments, repository config, comments, checkpoints, or evidence.
  • Revoke credentials you no longer use with notchlet mcp revoke.
