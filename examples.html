Practice

Use cases

Eight worked scenarios, from a no-account quick fix to a connected backlog feature with capability delta and visual evidence. Commands are shown in the order that keeps state valid.

1. Offline quick fix (no account)

Use a quick change when the work is small, local, and does not alter a shipped capability. The capability declaration is still explicit.

cd docs-repo
notchlet init

notchlet change new fix-typo --quick
notchlet change update fix-typo \
  --intent "Correct the broken install command." \
  --outcome "The install section shows a command that succeeds." \
  --capability-impact none \
  --capability-rationale "Documentation-only correction; no runtime capability changes."

notchlet change add fix-typo requirement --id R1 \
  --title "Install command works" --description "The documented command completes successfully."
notchlet change add fix-typo scenario --id S1 \
  --when "a reader runs the install command" --then "the CLI prints its version" --requirement R1
notchlet change add fix-typo check --id C1 \
  --description "CLI prints a version" --kind command \
  --command "notchlet --version" --requirement R1 --scenario S1
notchlet change add fix-typo task --id T1 \
  --title "Update install section" --requirement R1

notchlet validate fix-typo
notchlet task start T1 --change fix-typo
# edit the document
notchlet verify fix-typo --record
notchlet task complete T1 --change fix-typo --require-evidence
notchlet change close fix-typo --preview
notchlet change close fix-typo
Why this shape

Quick schema, explicit no-impact rationale, one runnable check, and closure without a capability baseline. No account, MCP, or network is involved.

2. Standard feature with a capability delta

Use the standard schema when the change alters what the product can do. Capture the capability baseline before authoring delta operations.

notchlet change new csv-export
notchlet change update csv-export \
  --intent "Let users export report tables as CSV." \
  --outcome "A report page offers CSV export and downloads the visible columns."

notchlet change add csv-export requirement --id R1 \
  --title "CSV export" --description "Report tables export to CSV with a header row."
notchlet change add csv-export scenario --id S1 \
  --when "a user chooses Export CSV" --then "a UTF-8 CSV downloads with the visible columns" --requirement R1
notchlet change add csv-export decision --id D1 \
  --decision "Generate CSV in the backend." \
  --rationale "Keeps formatting, encoding, and access control in one place."
notchlet change add csv-export check --id C1 \
  --description "CSV integration test" --kind command \
  --command "node --test test/export.test.mjs" --requirement R1 --scenario S1
notchlet change add csv-export check --id C2 \
  --description "Download endpoint" --kind http \
  --url "http://127.0.0.1:4173/api/reports/1/export.csv" \
  --expected-status 200 --expected-header "Content-Type: text/csv" --requirement R1
notchlet change add csv-export task --id T1 \
  --title "Backend export endpoint" --requirement R1
notchlet change add csv-export task --id T2 \
  --title "Frontend export action" --requirement R1 --depends-on T1

notchlet change baseline csv-export
notchlet change delta csv-export add --requirement R1 \
  --rationale "Reports gain a CSV export capability."
notchlet change render csv-export --write
notchlet validate csv-export
notchlet task start T1 --change csv-export
notchlet task complete T1 --change csv-export
notchlet task start T2 --change csv-export
notchlet task complete T2 --change csv-export

notchlet verify csv-export --serve --record --repeat 2
notchlet evidence list --change csv-export --requirement R1
notchlet change close csv-export --preview
notchlet change close csv-export --baseline-revision 1
Why this shape

Standard requirements force full scenario coverage and a design decision. The delta operation snapshots the capability change, and closure names the baseline revision captured before implementation.

3. Backlog-driven feature from the platform

When the item already exists, import it instead of retyping requirements. MCP supplies bounded context; the CLI owns local state.

notchlet workspace info
# confirm server, product, repository

# optional: read context through MCP in the connected client
# backlog_get({ itemId: 842 }) or notchlet_backlog_get in OpenCode

notchlet backlog import NOT-142
notchlet status NOT-142
notchlet instructions NOT-142 --action plan
notchlet validate NOT-142

notchlet task start T1 --change NOT-142
# implement
notchlet verify NOT-142 --serve --record
notchlet task complete T1 --change NOT-142 --require-evidence

notchlet checkpoint --change NOT-142 --name "Implementation verified" \
  --summary "Endpoint and UI done; integration tests pass."
notchlet change close NOT-142 --preview
notchlet sync push --change NOT-142

# Delivery is a separate, explicit step after review and merge:
# development_delivery_create with expectedRevision, operationId,
# payloadHash, snapshotRevision, and target.
Merge is not deployment

Before a DONE request for branch-linked work, verify the exact PR or MR is merged and approved. Delivery evaluation does not merge, deploy, or publish anything.

4. Resume work without restarting

Resume is the default for any continuation. Read state, then continue only eligible tasks.

cd existing-project
notchlet change list
notchlet status checkout-flow
notchlet instructions checkout-flow --action resume

# The instructions identify the next eligible task and any blockers.
notchlet task start T3 --change checkout-flow
notchlet verify checkout-flow --serve --record
notchlet task complete T3 --change checkout-flow --require-evidence
Do not replay

Do not reinitialize the workspace, recreate the plan, or reconfigure MCP while the existing binding and change remain valid.

5. Revise requirements mid-change

Requirements change. Preserve stable IDs and existing progress, then revalidate and re-verify.

notchlet instructions checkout-flow --action revise

notchlet change update checkout-flow requirement R2 \
  --description "Saved cards may be removed; removal requires confirmation."

notchlet change add checkout-flow scenario --id S4 \
  --when "a user removes a saved card" --then "removal is confirmed and the card disappears" \
  --requirement R2

# If the requirement belongs to a declared capability delta, re-author the snapshot.
notchlet change delta checkout-flow update --requirement R2 \
  --rationale "Removal confirmation added."

notchlet change render checkout-flow --write
notchlet validate checkout-flow
notchlet verify checkout-flow --serve --record

Existing task progress is preserved when editing an item in place with change update <change> <kind> <id>. Task status changes still go through task start|complete.

6. Visual acceptance criteria

For layout, accessibility, or visual behavior, attach a capture to the evidence record. This is separate from the check result and does not replace it.

notchlet change add checkout-flow check --id C5 \
  --description "Checkout page renders totals" --kind ui \
  --url "http://127.0.0.1:4173/checkout" \
  --expected-text "Order total" --requirement R3

notchlet verify checkout-flow --serve --record \
  --capture-url "http://127.0.0.1:4173/checkout" \
  --viewport 1280x800 --wait-for "#totals" --full-page
# or attach an existing artifact
notchlet verify checkout-flow --record --attach artifacts/checkout.png
  • --ui-capture on-failure is the default for UI checks; use always or never deliberately.
  • Evidence attachments should contain no credentials, tokens, or production personal data.

7. Review another agent's change

Review is a gate, not a formality. Inspect the diff and the actual test output, not the summary.

notchlet status checkout-flow
notchlet evidence list --change checkout-flow --requirement R1,R2
notchlet change show checkout-flow

# inspect the diff and run the focused checks yourself
git diff origin/main...HEAD
node --test test/checkout.test.mjs
OutcomeAction
ApproveAll criteria covered, checks pass, no scope creep. Keep or set IN_REVIEW and let delivery proceed.
Request changesComment with specific items on the PR and item. Do not close or set DONE; return to implementation.
DisputeDiscuss on the item comment thread, not private messages. Re-review only the changed files and feedback items.

8. Set up MCP from scratch

OpenCode, connected

notchlet auth login --server https://pg-api.mbintangr.com
notchlet mcp configure --client opencode
notchlet mcp status
notchlet doctor
# restart OpenCode, then verify the notchlet_* tools appear

Claude Code, connected

notchlet auth login --server https://pg-api.mbintangr.com
notchlet mcp configure --client claude
notchlet mcp status
# restart Claude Code; tools appear as mcp__notchlet__*

Offline, no account

notchlet init --local --client opencode
notchlet mcp status
notchlet mcp serve --local   # the client may start this itself
Credential rule

Remote configs must reference the token through an environment variable ({env:NOTCHLET_MCP_TOKEN} or ${NOTCHLET_MCP_TOKEN}). If you print the token with notchlet mcp token, treat it as a secret: do not paste it into prompts, commits, comments, or evidence.

If the client shows no tools, check notchlet mcp status, confirm the config file belongs to the client you are using, and restart the session. Do not probe /mcp with an unauthenticated GET.
