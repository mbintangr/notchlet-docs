Notchlet CLI

The CLI owns local change state: authoring, revisions, tasks, verification, evidence, closure, and explicit synchronization. It reports notchlet 1.0.1 · @notchlet/core 1.0.0 and requires Node.js 22 or newer.

Install and verify

npm install -g @notchlet/cli
notchlet --version
# notchlet 1.0.1 · @notchlet/core 1.0.0

# or without a global install
npx @notchlet/cli --version
Global options

--json prints a machine envelope. --workspace <root> or --root <root> selects the workspace. --server <url> overrides the default server. --version prints CLI and core versions.

With --json, the envelope reports whether the command executed. For verification, inspect data.result or data.verification.outcome rather than ok alone.

Requires an authenticated user session and an existing team; the checkout's Git remote is connected automatically. --create is the explicit authorization for the product/repository writes; --dry-run resolves and prints the plan with zero POSTs.

Bootstrap only when required

Use the nearest existing workspace. Run notchlet init only when a workspace is genuinely missing and the user approves it; there is no separate bootstrap command.

Product create is idempotent by slug

bind --create derives a team-scoped slug from --name unless --slug is given. An exact name or slug match adopts the existing product; a 409 conflict re-lists by team and slug and adopts the single match. The create is journaled under .notchlet/.local/bootstrap/ before the POST, so an uncertain response is resolved by lookup, never a blind retry. The Git remote URL is normalized to a credential-free HTTPS URL; no access token is sent and the webhook secret is never printed. Organization and team creation stays platform-only.

Verification records a Git observation when the workspace is a repository. A non-Git workspace records a bounded source fingerprint with each evidence item (hashes only; metadata, dependencies, environment files, and credentials are excluded), so source edits stale evidence without Git. change close --preview prints Source binding: source bound means every current check observes either Git or that workspace fingerprint; source unbound means legacy or artifact-only evidence. Unbound current evidence blocks closure with artifact_basis_unacknowledged until you either re-record checks after binding source or pass --accept-artifact-basis; an accepted close records acceptedArtifactBasis: true in the closure manifest.

Rendering and plans

notchlet change render <change> --check    # report artifact drift
notchlet change render <change> --write    # rewrite from the model; bumps revision once
notchlet change render <change> --write --force   # overwrite unmarked hand-authored files
notchlet change render <change> --tree --write  # render every open node in the subtree
notchlet change render <change> --tree --check  # report drift across the subtree
notchlet change plan validate <plan.json>
notchlet change plan status <change>
notchlet change plan sync <change>       # accept the current plan hash after review

Declared proposal.md and spec.md views render from the model. Generated files carry a marker; --write refuses unmarked hand-authored files unless you pass --force. Use notchlet schema to list or print shipped JSON schemas.

Plan provenance tracks both single-change plans and backlog tree plans. A change imported from a tree keeps the tree file as its source plan, so change plan status validates the whole tree and reports a node that was removed or renamed as drift; closure follows the same rule and records the drift decision in closure.json.

Verification and evidence

notchlet verify <change> [--check C1,C2] [--record] [--requirement R1] [--task T1]
notchlet verify <change> --serve [--repeat 2] [--setup "node seed.mjs"] [--teardown "..."]
notchlet verify <parent> --tree [--record] [--serve]
notchlet verify <change> --record --capture-url http://127.0.0.1:4173/ --full-page
notchlet change add <change> check --id C1 --description "Register is ready" --kind ui --url http://127.0.0.1:4173/ --wait-for "#app" --expected-visible-selector "#product-grid" --expected-hidden-selector "#receipt-dialog"
notchlet evidence list --change <change> [--check C1] [--requirement R1] [--task T1] [--stale] [--failed]
notchlet evidence record --change <change> --summary "..." --kind manual --outcome passed

Prefer an owned run

--serve gives the run a known start state. Reusing a server can hide drift, and repeated runs detect state-dependent failures that a single green run misses.

Verifying a tree

Use verify <parent> --tree to run every open node's own checks with its persisted setup and serve command. Nodes run deepest-first, then by path; this is a deterministic run order, not task dependency order. Tree runs share the workspace, environment, and external app or data state, so stateful checks should reset state with per-node setup/teardown or isolated data directories. The output prints the run order, aggregate observation basis, and each child's basis, advisories, artifact drift, and render recovery. A failed node also prints its failed check IDs, failed assertions, failure phase, evidence log path, and single-node recovery, so the failure is diagnosable without rerunning the leaf. An archived-only subtree exits 2 with no_open_nodes and points to change restore instead of suggesting a new check on an archived leaf. If the nodes share one running app instead, start it once with verify <node> --serve --keep-running, then verify nodes individually with --reuse-serve (setup is skipped) and stop the app yourself. --tree applies --ui-capture, --full-page, --settle-ms, browser/viewport, and runtime flags to every node, but rejects per-check selection and assertion overrides, setup and serve overrides, and --capture-url/--attach; verify a single node for those.

Presence is not visibility

--expected-selector only proves markup exists; hidden dialogs and display: none panels still match. Prove the rendered state with --expected-visible-selector, --expected-hidden-selector, and --expected-enabled-selector.

Hidden also means absent

--expected-hidden-selector passes when the element is present but not rendered, and also when it is not in the DOM at all. The assertion reports hidden or absent so the difference stays visible. A check that only asserts hidden selectors treats absence as deliberate and emits no hint. When a check also asserts positive rendered state, verify hints if a hidden pass came from absence; pair it with --expected-selector on the same selector when hidden-but-present is required.

--expected-absent-selector asserts strict DOM absence: present-but-hidden fails. Use it for removed dialogs or permission-gated controls. A change whose only check asserts hidden or absent elements raises a hidden_only_sole_check advisory, because a blank page could pass; add a positive visibility or text assertion.

Planning fields, sidecar v2, and divergence

Linked backlog nodes reconcile planning fields (title, description, priority, points, start/due) three ways against the sidecar's sync baselines: remote == baseline and local changed means push; local == baseline and remote changed means adopt into platform observations on pull; both changed differently is a field_divergence warning — the field is skipped and reported, never silently overwritten. Description updates carry an expected revision so a concurrent platform edit fails closed. The sidecar schema is v2 (v1 files still read and upgrade lazily); older CLIs reject v2 with unsupported_version and an upgrade hint.

Resolution is explicit

A divergence is resolved by pulling and adopting the remote value or re-applying the local one with backlog set — never by force-overwrite.

A complete local session

notchlet init
notchlet change new search-endpoint --quick
notchlet change update search-endpoint \
  --intent "Expose search over items." \
  --outcome "GET /search?q= returns matching item names in order." \
  --capability-impact none \
  --capability-rationale "Internal spike; not yet a shipped capability." \
  --run-command "node server.mjs" \
  --preview-url "http://127.0.0.1:4173/" \
  --readiness-url "http://127.0.0.1:4173/health" \
  --environment PORT=4173

notchlet change add search-endpoint requirement --id R1 \
  --title "Search endpoint" --description "Returns items whose name contains q."
notchlet change add search-endpoint scenario --id S1 \
  --when "q matches two items" --then "both are returned in name order" --requirement R1
notchlet change add search-endpoint check --id C1 \
  --description "search tests" --kind command \
  --command "node --test test/search.test.mjs" --requirement R1 --scenario S1
notchlet change add search-endpoint task --id T1 \
  --title "Implement endpoint" --requirement R1

notchlet validate search-endpoint
notchlet task start T1 --change search-endpoint
# implement, run focused tests
notchlet verify search-endpoint --serve --record
notchlet task complete T1 --change search-endpoint --require-evidence
notchlet change close search-endpoint --preview
notchlet change close search-endpoint
Never invent results

Do not report a check as passing unless it ran and passed. Distinguish failures caused by your change from pre-existing failures, and record blockers instead of hiding them.
