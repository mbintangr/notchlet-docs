Notchlet CLI

The CLI owns local change state: authoring, revisions, tasks, verification, evidence, closure, and explicit synchronization. It reports notchlet 1.0.0 · @notchlet/core 1.0.0 and requires Node.js 22 or newer.

Install and verify

npm install -g @notchlet/cli
notchlet --version
# notchlet 1.0.0 · @notchlet/core 1.0.0

# or without a global install
npx @notchlet/cli --version
Global options

--json prints a machine envelope. --workspace <root> or --root <root> selects the workspace. --server <url> overrides the default server. --version prints CLI and core versions.

With --json, the envelope reports whether the command executed. For verification, inspect data.result or data.verification.outcome rather than ok alone.

Setup, auth, and workspace

CommandPurpose
notchlet init [path] [--local|--interactive]Create a workspace. Local-only by default. --client opencode|claude also installs skills and local MCP config.
notchlet auth login --server <url>Log in and store a profile. Add --allow-file-token-store only where appropriate.
notchlet auth status · auth logout · profile use --server <url>Inspect, remove, or switch authentication profiles.
notchlet workspace bind --server <url> [--product <name>] [--repository <name>] [--rebind]Bind the checkout to a product and repository. Prefer names; the server resolves them.
notchlet workspace infoShow the current binding and workspace configuration.
notchlet doctorDiagnose workspace, binding, server connectivity, and authenticated capabilities.
Bootstrap only when required

Use the nearest existing workspace. Run notchlet init only when a workspace is genuinely missing and the user approves it; there is no separate bootstrap command.

Authoring commands and flags

notchlet change update <change> --intent "..." --outcome "..."
notchlet change update <change> requirement R1 --description "Refined wording"
notchlet change update <change> --run-command "node server.mjs" \
  --preview-url "http://127.0.0.1:4173/" --readiness-url "http://127.0.0.1:4173/health" \
  --ready-timeout 20000 --ready-interval 100 --environment PORT=4173

notchlet change add <change> requirement|scenario|decision|check|task [options]
notchlet change remove <change> <kind> <item-id> [--revision <n>]
notchlet change apply <change> --file <plan.json> [--revision <n>]

change apply applies an ordered { expectedRevision, operations } batch atomically: the batch validates against the final state, writes once, bumps the revision once, and rolls back on failure. Capability delta operations are not valid batch entries.

--expected-body-contains, --expected-json, --expected-json-contains, --expected-json-at, --expected-headerhttp checkBody, JSON subset/containment/path, and header assertions.

Rendering and plans

notchlet change render <change> --check    # report artifact drift
notchlet change render <change> --write    # rewrite from the model; bumps revision once
notchlet change render <change> --write --force   # overwrite unmarked hand-authored files
notchlet change plan validate <plan.json>
notchlet change plan status <change>
notchlet change plan sync <change>       # accept the current plan hash after review

Declared proposal.md and spec.md views render from the model. Generated files carry a marker; --write refuses unmarked hand-authored files unless you pass --force. Use notchlet schema to list or print shipped JSON schemas.

Verification and evidence

notchlet verify <change> [--check C1,C2] [--record] [--requirement R1] [--task T1]
notchlet verify <change> --serve [--repeat 2] [--setup "node seed.mjs"] [--teardown "..."]
notchlet verify <change> --record --capture-url http://127.0.0.1:4173/ --full-page
notchlet evidence list --change <change> [--check C1] [--requirement R1] [--task T1] [--stale] [--failed]
notchlet evidence record --change <change> --summary "..." --kind manual --outcome passed
FlagEffect
--serveStart the declared run command, wait for readiness, run checks, then stop the server.
--serve-commandStart a different command than the change run metadata.
--repeat <n>Rerun the batch (including setup) and report state-dependent failures.
--check-setup-idempotence --setup-state <path>Fail when setup does not reproduce the declared state.
--reuse-serveTarget an existing server; setup is skipped.
--ui-capture never|on-failure|alwaysArchive UI captures for UI checks.
--capture-urlWith --record, capture a settled screenshot and DOM snapshot.
--attach <path>Attach a file to recorded evidence (screenshots, logs, reports).
--timeout <ms>Per-check timeout; default 120000.
Prefer an owned run

--serve gives the run a known start state. Reusing a server can hide drift, and repeated runs detect state-dependent failures that a single green run misses.

A complete local session

notchlet init
notchlet change new search-endpoint --quick
notchlet change update search-endpoint \
  --intent "Expose search over items." \
  --outcome "GET /search?q= returns matching item names in order." \
  --capability-impact none \
  --capability-rationale "Internal spike; not yet a shipped capability." \
  --run-command "node server.mjs" \
  --preview-url "http://127.0.0.1:4173/" \
  --readiness-url "http://127.0.0.1:4173/health" \
  --environment PORT=4173

notchlet change add search-endpoint requirement --id R1 \
  --title "Search endpoint" --description "Returns items whose name contains q."
notchlet change add search-endpoint scenario --id S1 \
  --when "q matches two items" --then "both are returned in name order" --requirement R1
notchlet change add search-endpoint check --id C1 \
  --description "search tests" --kind command \
  --command "node --test test/search.test.mjs" --requirement R1 --scenario S1
notchlet change add search-endpoint task --id T1 \
  --title "Implement endpoint" --requirement R1

notchlet validate search-endpoint
notchlet task start T1 --change search-endpoint
# implement, run focused tests
notchlet verify search-endpoint --serve --record
notchlet task complete T1 --change search-endpoint --require-evidence
notchlet change close search-endpoint --preview
notchlet change close search-endpoint
Never invent results

Do not report a check as passing unless it ran and passed. Distinguish failures caused by your change from pre-existing failures, and record blockers instead of hiding them.
